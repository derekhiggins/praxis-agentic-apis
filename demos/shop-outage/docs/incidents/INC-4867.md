# Incident report INC-4867: checkout outage after database credential rotation

Severity: SEV1
Status: mitigated; action item open
Duration: 47 minutes
Services: storefront, checkout-api, orders-db

## Summary

Customers could browse the shop but every checkout failed with an error page.
The weekly Vault rotation changed the `checkout` role password and restarted
orders-db. checkout-api pods kept the old password from their environment
variables, failed database authentication, and went NotReady. With no ready
endpoints behind the `checkout-api` Service, storefront returned 502 for
`POST /checkout`.

## Timeline (UTC)

- 15:00 Vault rotation job updates `orders-db-credentials` and restarts orders-db.
- 15:01 checkout-api readiness probes start failing; pods 0/1 Ready.
- 15:03 storefront 5xx alert fires for `/checkout`.
- 15:20 on-call suspects orders-db; database is healthy.
- 15:41 orders-db logs show `password authentication failed for user "checkout"`.
- 15:46 checkout-api pods deleted one at a time; new pods Ready, checkout recovers.

## Root cause

Kubernetes resolves Secret values used in environment variables when the
container starts. Updating the Secret does not change the environment of
running containers. checkout-api has no reload mechanism.

## Evidence

- checkout-api: `psycopg2.OperationalError: connection to server at "orders-db" ...
  FATAL:  password authentication failed for user "checkout"`.
- orders-db: matching FATAL and DETAIL pg_hba.conf lines; restart at 15:00.
- storefront: `upstream=checkout-api:8080 upstream_status=- error="[Errno 111]
  Connection refused"`.

## Action items

- Payments Platform: add `secret.reloader.stakater.com/reload:
  orders-db-credentials` to checkout-api. Status: open.
- Data Platform: rotation job to post in #payments-platform. Status: done.
- Lesson: check orders-db logs for authentication failures before debugging
  the network.
